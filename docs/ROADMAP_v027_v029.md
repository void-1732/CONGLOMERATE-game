## B. 現行Ver.0.26で直接確認した接続点と制約

- 既存10項目：`DESIGN_FIELDS` / `DESIGN_DEFAULT` / `designAnalysis` / `materialRequirement` / `productCostQuote`。800研究ノード・`techBenefits`を保持。
- 工場：`f.plants`、`f.factoryOps`、`factoryLaborPlanV026`、従来共通部品と詳細3モジュール（`V21_MODULE_TYPES`）を使用中。**新しい6系統の部品とは別物**として扱う。
- 調達：`ensureSupplyNetwork` / `procureNetwork` は既存法人を仕入先ノードとして列挙するが、**そのノードの供給能力・発注だけで、売り手法人の現物在庫・売上・売掛を必ずしも記録していない**。NEXT-006では新しい実物取引台帳が必要。
- 会計：`post` は**各社の現地通貨の最小単位（整数、ゲーム内では1/100通貨単位）**の複式仕訳。`ACCTYPE`には `materials`, `materialsTransit`, `wip`, `goods`, `ar`, `payable`, `sales`, `cogs` がある。帳簿・補助台帳を必ず照合。
- 連結：`consolidate` は既存 `s.intercompanyTx` の `kind:'goods'` と内部貸付・利息を扱う。**部品が車両に組み込まれた後の未実現利益を自動消去する仕組みはない**。NEXT-006では新しい部品取引の明細と消去計算の拡張が必須。
- 保存：JSON封筒 `{format:'CONGLOMERATE', version:1, checksum, payload}`、`parsePayload`。既存 `ensure*` による補完と、IndexedDBの複数世代保存を保持。
- 月次：`runMonth` は `structuredClone` で試算→工程別処理→`check`→`consolidate`→確定→`saveAuto`。**確定前失敗で旧Sへ戻る性質、確定後の保存失敗表示、同一月の二重実行防止**を維持。
- 既存M&A・株主構成・新株発行で子会社の支配関係が変わるため、権利の有効性を固定の親子関係に依存させない。

## C. 単一の正本とデータ構造（Ver.0.27）

**前回の暫定的な `f.componentLibrary` 等を、同一部品／契約の多重複製を防ぐため次の構成へ精緻化する。**

```ts
s.partEconomy = {
  schemaVersion: 1,
  nextSerial: 1,
  specs: [],          // 部品設計の改訂ごとの不変スナップショット
  licenses: [],       // 設計利用・製造許可の正本
  contracts: [],      // 法人間契約の正本
  orders: [],         // 注文・引当・発送・検収の状態
  shipments: [],      // 一意IDを持つ輸送・保有権状態
  tradeEvents: []     // 仕訳参照、売上・費用・消去情報
};
f.partOperations = {
  projects: [],       // 設計変更・量産化プロジェクト
  inventoryLots: [],  // 法人・工場・部品改訂・数量・簿価・原価系譜
  productionPlans: [],
  approvedModels: []
};
m.componentMode = 'legacy' | 'detailed';
m.bom = {revision, status, lines:[{specId,revision,quantity}], approvedAt};
```

- 部品仕様キー = `specId + revision`。仕様改訂は上書きでなく**新レコード**。車種BOMは承認した版に固定。
- 設計権利者 `ownerFirmId`、製造者 `producerFirmId`、現物所有者 `inventoryOwnerFirmId` は必ず区別。
- `s.partEconomy` は取引の唯一の正本。各企業の画面は自社視点で参照し、同じ契約を買い手／売り手の双方へ複製保存しない。
- `f.partOperations.inventoryLots` は `materials` / `materialsTransit` / `wip` の**内訳補助台帳**であり、同額の新しい総勘定元帳資産を無断で追加しない。工場別・法人別の分解値が科目残高と一致することを確認する。
- 固定済み旧車種は `componentMode:'legacy'`。`factoryOps.mode`（従来／詳細3モジュール方式）とは**独立した設定**。旧車種には新BOM原価を重複適用しない。
- `ensureV27` は**冪等・無乱数・無出金・無業績更新**。旧セーブを複製して移行→検証→採用する。元JSON、旧自動保存世代、既存IDを保護する。
- 新規IDは名前空間 `PART-`, `BOM-`, `LIC-`, `ORD-`, `LOT-`, `TRD-` で発番し、再読込後も衝突しない。移行時に不必要なシリアルを発行しない。

## D. NEXT-004：設計不適合の修正開発（Ver.0.28）

### 適合判定

1. **技術条件**：800研究ノードの前提・時代・認証条件を確認。未研究は「解禁待ち」であり追加料金だけで突破できない。
2. **取付・寸法**：車台側の搭載包絡、マウントコード、許容重量、車体寸法を比較。
3. **駆動系**：エンジン／モーター出力と変速機許容トルク、駆動方式・電圧規格を比較。
4. **品質・耐久**：部品の寿命／強度／冷却・安全余裕を検証。
5. 判定は `OK / MODIFIABLE / RESEARCH_LOCK / INFEASIBLE` の4区分。`MODIFIABLE`のみ修正プロジェクト候補。`INFEASIBLE`は新部品を選ぶか基礎設計を改める。

### 修正プロジェクト

- プレビュー：不適合項目、実行可能な修正案、**旧版と新版の性能差・重量差・単価差**、追加開発費、必要月数、工場再適合の要否。
- ユーザー承認→必要資金・研究・設計枠の再判定→費用記帳→`componentProject`登録→月末進捗→完了後に新 `spec revision` を作成→BOM再審査。
- 改修中のBOMは本番生産不可。費用は現行の研究開発費勘定を原則とし、未承認の資産計上を自動的に行わない。
- 修正完了で他車種・他社が使う**既存部品改訂は変えない**。新改訂を選ぶ意思決定が必要。
- 開発枠の占有方法と工期係数は質問7で確定。費用は年代・部品難度・不適合量から見積り、最大／最小／例外を単体テストで校正する。

## E. NEXT-005：グループ内共有と権利管理（Ver.0.28〜0.29）

### 権利のレイヤー

| 対象 | 説明 |
|---|---|
| 設計の権利 | 部品仕様の開発元法人・著作／特許等の管理主体。M&A後も原則その法人に帰属。 |
| 詳細情報の閲覧 | グループ会社の検索・設計参考へのアクセス許可。 |
| 製造ライセンス | 指定法人・工場・部品改訂が自社工場で製造する権利。 |
| 製品への採用 | 指定法人の車種BOMでその部品を使う権利。完成品の購入とは別。 |
| 現物所有権 | ロットとして実際に持つ部品在庫。ライセンスと無関係。 |

- グループ内共有は `controlSet` 等の現在の議決権支配判定を参照。間接支配・複数子会社・少数株主の存在を考慮する。
- **自動的に権利を移転しない。** 利用開始時にライセンス契約（grant）を作成し、権利者、利用者、部品改訂、用途、開始月、有効期限、利用対価、承認者を保存。
- グループ外転出／支配権喪失時は新規許可を止めるか再契約を要求。**すでに完成・販売した車両や既存の法的契約を遡及的に消すことはしない。** 契約終了後の継続量産条件は契約規約で明示。
- 物理部品を購入しても、その設計をコピー・製造する権利は自動付与しない。
- 複数法人の共通設計を使い回しても、試験費・設備転換・製造費・ライセンス費を同じ一括値として二重計上しない。
- グループ内対価の方針（無償・費用分担・使用料など）は質問8で決定するまでは仮値に留める。

## F. NEXT-006：実際の企業間部品売買（Ver.0.29）

### 契約〜納入〜回収

1. **供給能力の確認**：売り手はゲーム内法人で、対象部品の製造権／製造設備／利用可能在庫（既予約分を除く）が必要。現行の取引ノードにある抽象的な能力だけで「実在庫」と見なさない。
2. **注文（ORDERED）**：買い手・売り手・部品改訂・数量・価格・通貨・出荷地・納入地・リードタイム・支払条件・一意の注文IDを固定。売り手の予約在庫を増やし、二重引当を禁止。
3. **発送（IN_TRANSIT）**：売り手の出荷可能ロットを減らし、売り手所有の輸送中在庫へ振替。原則として到着検収まで売上を確定しない。紛失・事故・キャンセルの処理は専用状態へ移動。
4. **納入検収（ACCEPTED）**：その月の到着分について、売り手は売上・売掛と売上原価を、買い手は原価付き部品在庫・買掛を同時記録。注文の検収済み数量を増やす。
5. **支払（SETTLED）**：売掛／買掛が消えるまで一意の決済IDで管理。資金不足のときは負の現金を作らず未払として残し、期限超過状態を記録。返金・返品・取消しも元取引を参照する逆仕訳で処理。

**同一企業の工場間移動**は売上を作らず簿価移管。**別法人の子会社間売買**は単体で通常の販売／仕入とし、連結上だけ内部取引を消去。

### 同一通貨取引の仕訳例（単位は各社現地通貨の最小単位、例示）

売り手の原価100、販売価格140、買い手が未販売の部品1個を受領した場合：

| 時点 | 売り手の仕訳 | 買い手の仕訳 |
|---|---|---|
| 発送 | `借 materialsTransit 100 / 貸 materials 100` | なし（所有権未移転） |
| 検収 | `借 ar 140 / 貸 sales 140`；`借 cogs 100 / 貸 materialsTransit 100` | `借 materials 140 / 貸 payable 140` |
| 支払 | `借 cash 140 / 貸 ar 140` | `借 payable 140 / 貸 cash 140` |

この場合、連結対象の親子・兄弟会社間なら、**売上140・対応原価100・未販売在庫に残る内部利益40、内部売掛／買掛140、内部現金の受払を消去**する。未販売の部品が車両の仕掛品・完成車在庫へ移行した後も、外部顧客に実販売されるまでは40の内部利益を追跡する。

### 原価系譜・消去

- 既存 `s.intercompanyTx(kind:'goods')` の処理を壊さず、`tradeEvents(kind:'component')` を追加。売り手在庫ロット→出荷→買い手部品ロット→組立BOM→完成車ロット→販売まで**出所・内部利益の移動先を追跡**。
- 連結表示の未実現利益、内部売上／売上原価、債権・債務、月次内部現金決済を重複消去しない。少数株主持分への帰属も検証。
- 国際取引は発注時・検収時・決済時・月末換算のレートを明示し、**双方の現地通貨金額を個別整数仕訳**。外貨差損益・換算差が合致するまで国際の実会計取引を公開せず、まず同一通貨で検証する。これは恒久的な地域制限ではなく品質ゲート。
- 独立AI企業が部品供給能力を確保する範囲は質問9で決定する。実体を持たない外部供給者について、ゲーム内の架空法人の売上・現金を創作しない。

## G. 改訂した実装順序・月次工程

### Ver.0.27 — 保護・移行のための基盤

1. Ver.0.26の`index.html`、代表旧セーブ、研究800 ID一覧、現金／在庫／株式／工場状態の比較表を固定。
2. スキーマ補完 `ensureV27`、一意ID、新台帳、参照整合性・保存テストのみ導入。**旧車種の実際の製造・販売には一切接続しない**。
3. 移行を二度行っても結果・発番・金額が変わらないことを試験。旧セーブへの書き戻し・上書きは行わない。
4. 合格後に限り次版へ進む。開発ブランチで作業し、GitHub `main` は検証済みビルドだけを反映。

### Ver.0.28 — 独立部品・修正開発・権利

1. 6系統の部品設計、改訂、10項目基本設計と任意の詳細設計画面を追加。
2. 部品適合検査→追加費用・工期見積→承認→開発→再検査を実装。
3. 権利者・ライセンス・製造権・設計利用者の台帳と、現在の支配関係からの許可判定を実装。
4. 正式な量産BOMは改訂IDで凍結。ただし **Ver.0.29完了までは新方式の自動量産を開始しない**。

### Ver.0.29 — BOM量産・企業間在庫売買・会計

1. 工場設備適合・人員配分・原材料所要量・不良率から実際の部品製造ロットと実原価を算出。
2. 同一法人移管、子会社間売買、外部法人への発注／発送／検収／決済と在庫追跡を順番に有効化。
3. 現行 `runMonth` の複製状態内に新工程を配置：`PART_ORDER_PLAN`（AI計画後）、`PART_RECEIPTS`（資材調達後）、`PART_PRODUCTION`（専門部品生産）、`PART_DISPATCH`（自動物流）、`BOM_ASSEMBLY`（完成車生産）。売り手・買い手の操作を**同じ試算状態内**で完結。
4. 各モデルは `legacy` と `detailed` を排他的に選択。旧3モジュールと新BOMの双方を同じ完成車に消費させない。
5. `PART_*`が失敗した月は全法人・全工場・全取引状態を処理前へ戻す。月次確定後の自動保存失敗は計算失敗と分離し、二重計算を避ける。
6. グループ売買の内部利益・未払残高・未販売車両の原価系譜まで追跡し、単体・連結・CFを検証してから一般プレイに公開。

### Ver.0.30〜0.31との境界

- Ver.0.30で800技術の部品・製造個別効果と量産化を深化。**800技術のIDは固定**。
- Ver.0.31でNEXT-003の購買者再配分・競合流出・供給不足・価格弾力性を新しい市場計算へ導入。`総販売数 <= 月間需要`、`車種販売数 <= 販売可能在庫/販路容量`、顧客の二重割当ゼロを必須条件とする。

## I. 必須の品質ゲートと停止条件

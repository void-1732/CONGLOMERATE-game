# CONGLOMERATE 次世代改修・第1回確定仕様と Ver.0.27〜0.29 詳細実装計画

策定日：2026-11-17 ／ 基準：Ver.0.26（GitHub `main`）／ **設計文書のみ。ゲーム本体は未変更。**

## B. 現行コードの接続点・保護対象

- 車両10項目：`DESIGN_FIELDS`, `DESIGN_DEFAULT`, `designAnalysis`, `materialRequirement`, `productCostQuote`。
- 研究：800件のID、`f.research`, `techBenefits`、既存依存関係を保持。
- 工場：`f.plants`, `f.factoryOps`, `factoryLaborPlanV026`, 3種の詳細モジュール、既存工場物流を保持。
- 調達：`f.supply.contracts`, `s.supplyNetwork.nodes`, `procureNetwork`, 入荷・買掛・原材料仕訳を保持。
- 販売：`sellMonthly`, `segmentedDemandUnits`, `segmentCompatibility`, `sellGoods` と品質・市場実績を保持。
- 会計：`post`, `consolidate`, `check`、M&A、株主・増資・議決権、法人IDを保持。
- 保存：既存のJSON封筒 `{format:'CONGLOMERATE', version:1, checksum, payload}`、`parsePayload` とIndexedDB世代管理を維持。
- 月次：`runMonth`の複製状態→検算→確定→保存の二段階処理を変更しない。

## C. フェーズ別実装手順と合格条件

### Ver.0.27：スキーマ・移行・検証基盤

1. 現行Ver.0.26のコードと代表的なJSONを固定し、ゴールデン検証を記録。`dev/v027-components`等の開発用ブランチで作業。
2. 新規オブジェクト領域を用意：`f.componentLibrary`, `f.modelConfigurations`, `f.componentInventory`, `f.componentContracts`, `f.componentProjects`, `f.componentRights`。既存の`models`、`plants`、`stock`、`goods`に重複資産を作らない。
3. 旧車種には`componentMode:'legacy'`を設定（表示・計算とも旧挙動を維持）。新設計は明示的に`'detailed'`で開始。
4. 内部スキーマ改訂番号を追加。ただし外部セーブ封筒の`version:1`は維持。欠落項目を補完する**冪等**な移行関数を実装。
5. 旧セーブ読込→移行→検算→JSON再保存→再読込を試験。失敗時は旧セーブを破壊せず、明示エラーを表示。

**合格：** 800研究ID、旧車種、保有株式、会計残高、工場、AI設定の保持。移行を二度実行しても変化なし。旧車種の月次製造・販売をVer.0.26と比較して不意の差分なし。

### Ver.0.28：部品ライブラリ・車両詳細設計

1. 6系統（エンジン、変速機、車台、車体、電子装備、電池）に独立部品ID・改訂番号・権利者・実用化状況を設定。
2. 部品の性能、重量、寸法・取付規格、製造標準原価、耐久性、対応車種・駆動方式、必要技術を定義。
3. 車両10項目の基本設計の次に詳細設計モードを提供。標準構成の自動提案、共通部品候補、車種別の部品流用状況、適合警告、追加開発費・期間の見積りを表示。
4. 独自部品の開発・改訂と技術前提チェックを実装。設計不適合の確定処理は下記の質問4で決定。
5. 部品を実際の量産に投入する前に、部品別のBOM・試算を保存してプレビュー可能にする。Ver.0.29の量産移行が完了するまでは、未完成のBOMを実生産へ接続しない。

**合格：** 2車種で同一エンジン・車台IDを共有可能。変更時に他車種の既存量産BOMが勝手に変化しない。適合判定と見積りが再現可能。

### Ver.0.29：BOM量産・取引・原価・工場間物流

1. 車種・グレードのBOMを部品ID／改訂番号／必要数量で固定。`BOM → 購入／部品製造 → 工場別在庫 → 輸送中 → 到着 → 最終組立 → 完成車在庫`を実装。
2. 工場の対応設備・人員・製造原材料・生産上限・不良率を確認して部品製造指示を発行。工場別原価と部品共通化の効果を集計。
3. 自社工場間は簿価移動、グループ会社間は法人別仕訳と連結消去、外部購入は仕入・買掛と供給側の台帳（ゲーム内企業の場合）を記録。現行の7資材・3モジュール方式は旧車種向けに存続。
4. 単一車種に対し`legacy`原価計算と詳細BOM原価計算を**同時に適用しない**。詳細方式への変更はユーザー操作で明示する。
5. 新しい月次工程は`COMPONENT_RECEIPTS`, `COMPONENT_PRODUCTION`, `COMPONENT_TRANSFERS`, `BOM_ASSEMBLY`。既存月次トランザクション内で事前・事後検算し、失敗時は複製状態を破棄。

**合格：** 部品量の保存、在庫金額・仕訳の整合、グループ内部売買の連結消去、異常な重複製造・重複販売なし。旧方式の車種が混在しても正常に60か月進行。

## D. データモデル（提案）

```ts
ComponentSpec = {
  id, revision, ownerFirmId, category, name,
  attributes: { massKg, lengthMm, widthMm, heightMm, powerKw?, torqueNm?, capacityKWh?, durabilityIndex },
  interfaces: { sizeClass, mountCode, driveTypes, powerTypes },
  researchRequirements: [{techId, minimumLevel}],
  standardUnitCostBase, approvalStatus, licensePolicy
}
ModelConfiguration = {
  modelId, mode: 'legacy' | 'detailed', baseDesign10,
  partReferences: [{componentId, revision, quantity}],
  bomRevision, validationStatus, costEstimateBase
}
PartLot = {lotId, componentId, revision, firmId, plantId, quantity, bookValueLocal, status};
PartContract = {contractId, buyerFirmId, sellerFirmId?, partId, revision, quantity,
                unitPriceBase, leadMonths, status, deliveredQty, paymentsDue};
```

- EVの変速機、内燃機関車の電池などは方式に応じて不要・オプション扱いとし、全6部品を無条件必須にしない。
- 部品の権利・資産・在庫を分離。設計IDと製造ロットIDを同一視しない。
- 量産BOMは確定時に改訂番号を固定。部品の改良が過去モデルへ自動波及しないようにする。

## E. 計算方針（係数は未確定）

**互換性：** 車台寸法／搭載領域、駆動系・取付コード、エンジン最大トルクと変速機許容トルク、電力系統・電池搭載能力、研究前提のAND条件を検証。

**車両重量：** `基本車体重量 + Σ(部品重量×搭載数)`。品質・燃費・加速・原価は単独部品値ではなく構成全体で再計算。現行バランスからの逸脱を防ぐため、同等仕様の車両で旧計算との差分を校正する。

**部品製造単価：** `使用材料費 + 加工賃金 + 工場間接費 + 不良率に応じた良品当たり配賦額`。

**完成車実原価：** `Σ(使用部品の実際の在庫単価×BOM数量) + 組立人件費 + 検査費 + 必要な工場間接費`。材料費・運賃は決めた一つの勘定に一度だけ計上し、旧`materialRequirement`との二重引落しを禁止。

**需要配分（Ver.0.31導入）：** 国・顧客層別に月間購買希望台数`D`を設定し、所得適合、総保有費用（車両価格と燃料費等）、品質・耐久、ブランド、販売網、相対魅力度に応じた効用から希望車種を一次配分。売切れ・販売能力不足の希望者は同じ月に購入可能な代替車へ再配分。代替購入しない希望者は未充足とする。`合計実販売 ≤ D`、`実販売車種別 ≤ 販売可能在庫・販売網能力`を保証。

## F. UI指針

- 製品・開発：既存「設計・商品企画」内に基本10項目／部品詳細の切替。部品ライブラリ検索、車種間共通化、適合チェック、性能・原価差分プレビュー。
- 工場：工場一覧とBOM必要数量・部品製造／入荷・不足・ライン適合状況を1拠点詳細に集約。工場100拠点でも検索・状態絞り込み・ページ送りで使用。
- 調達：現行7原材料とは別に部品契約のタブ。売り手企業・価格・数量・納期・購入／内製の比較を提供。
- 市場：Ver.0.29では現行販売計算を維持。Ver.0.31で需要予測・価格シナリオ・顧客流出・供給不足を導入。

## G. 共通の品質ゲート

- 旧JSON複数世代の再読込・再保存・二重移行、チェックサム検証、失敗復旧。

- 旧製造のみ、BOM製造のみ、混在、100工場・20社以上のシナリオ。

- 各段階を開発ブランチで検証し、合格後のみGitHub`main`へマージ。旧版をGitタグとJSONバックアップで保護。
